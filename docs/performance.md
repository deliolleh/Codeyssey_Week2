# 문항이 늘어나면 어떻게 되나

기본 데이터는 50문항입니다. 문항이 1000개, 5000개로 늘었을 때 무엇이 먼저 문제가 되는지 실제로 재봤습니다.

측정 환경은 Python 3.13.9, macOS입니다.

## 저장·불러오기

| 문항 수 | `state.json` 크기 | 불러오기 | 저장 | 메모리(최대) |
|---:|---:|---:|---:|---:|
| 50 | 26 KB | 0.5 ms | 0.6 ms | 0.1 MB |
| 200 | 102 KB | 1.8 ms | 1.6 ms | 0.4 MB |
| **1000** | **510 KB** | **9.5 ms** | **7.2 ms** | **2.0 MB** |
| 5000 | 2,557 KB | 54.2 ms | 36.2 ms | 10.0 MB |

문항 수에 **정비례**합니다. 파일 전체를 한 번에 읽고 쓰기 때문입니다.

1000문항에서 불러오기 9.5 ms는 사람이 못 느끼는 수준입니다. 5000문항에서도 54 ms라 프로그램 시작이 느려졌다고 느끼기 어렵습니다.

메모리도 1000문항에 2 MB로, 파이썬 인터프리터가 기본으로 쓰는 14 MB에 비하면 작습니다.

## 번호로 퀴즈 찾기

`find_quiz()`는 목록을 처음부터 훑는 선형 탐색입니다. 없는 번호를 찾을 때가 최악입니다.

| 문항 수 | 선형 탐색 | 딕셔너리를 쓴다면 |
|---:|---:|---:|
| 50 | 0.9 µs | 0.058 µs |
| 200 | 3.1 µs | 0.048 µs |
| **1000** | **14.5 µs** | **0.046 µs** |
| 5000 | 69.3 µs | 0.190 µs |

선형 탐색은 문항 수에 비례해 늘고, 딕셔너리는 **거의 변하지 않습니다.** 1000문항에서 300배 차이가 납니다.

다만 **절대값이 작습니다.** 14.5 µs는 0.0145 ms이고, 이 함수는 퀴즈를 삭제할 때 한 번 호출됩니다. 사람이 번호를 입력하는 데 걸리는 시간이 이보다 백만 배쯤 깁니다.

그래서 지금은 고치지 않았습니다. 대신 **언제 고쳐야 하는지**는 분명합니다 — 한 번의 작업에서 이 탐색을 여러 번 반복하게 되면, 예를 들어 "특정 지역이 답인 문제를 모두 찾기" 같은 기능이 생기면 그때는 딕셔너리로 바꿔야 합니다.

```python
# 지금
def find_quiz(self, quiz_id):
    for quiz in self.quizzes:
        if quiz.quiz_id == quiz_id:
            return quiz
    return None

# 바꾼다면
self.quiz_index = {q.quiz_id: q for q in self.quizzes}   # 추가·삭제 때 함께 갱신
```

## 진짜 한계는 화면입니다

숫자로 보면 1000문항도 여유롭지만, 실제로 먼저 막히는 건 다른 곳입니다.

| 문항 수 | 목록 화면 줄 수 |
|---:|---:|
| 50 | 57줄 |
| 200 | 207줄 |
| **1000** | **1007줄** |

터미널 한 화면이 보통 40~60줄입니다. **50문항도 이미 한 화면을 넘고**, 실제로 이 프로젝트의 목록 스크린샷은 42번 문항에서 잘렸습니다.

1000문항이면 1007줄이 한꺼번에 쏟아집니다. 스크롤을 아무리 올려도 앞부분은 터미널 버퍼에서 밀려 사라집니다. **읽을 수 없는 출력은 없는 것과 같습니다.**

즉 이 프로그램에서 먼저 손봐야 할 것은 탐색 속도가 아니라 **목록을 보여주는 방식**입니다.

- 한 번에 20개씩 끊어 보여주고 Enter로 넘기기
- 유형·난이도로 걸러 보기
- 문제 문장에 포함된 낱말로 찾기

세 가지 모두 "출력량을 줄이는" 방향입니다.

## 연승전 자체는 영향이 적습니다

한 판에 출제하는 문제 수를 사용자가 정하기 때문입니다. 1000문항이 등록돼 있어도 10문제에 도전하면 화면에 나오는 건 10문제뿐입니다.

출제 순서를 섞는 `random.shuffle`도 1000문항에서 0.15 ms로 부담이 없습니다.

## 정리

| 항목 | 1000문항 | 판단 |
|---|---|---|
| 불러오기·저장 | 9.5 ms / 7.2 ms | 문제없음 |
| 메모리 | 2 MB | 문제없음 |
| 번호 탐색 | 14.5 µs | 지금은 문제없음. 반복 호출이 생기면 딕셔너리로 |
| **목록 출력** | **1007줄** | **먼저 막히는 지점. 페이지 나누기·검색 필요** |

성능 한계보다 **화면이라는 물리적 제약**이 먼저 옵니다. 이 프로그램에서 1000문항을 감당하려면 알고리즘을 바꾸기 전에 보여주는 방식을 바꿔야 합니다.
